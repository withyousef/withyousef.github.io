Start with the shape of the data

A conversation belongs to a contact and a channel. Messages hang off it with a direction and a delivery status, so the inbox, the CRM view and the reporting all read from the same rows.

Indexes follow the queries the UI actually makes: the inbox sorts by contact and latest activity, so that pair is indexed.

prisma/schema.prismaprisma
model Conversation {
  id         String    @id @default(cuid())
  channel    Channel   // WHATSAPP | INSTAGRAM | MESSENGER | TELEGRAM
  contactId  String
  contact    Contact   @relation(fields: [contactId], references: [id])
  messages   Message[]
  updatedAt  DateTime  @updatedAt

  @@index([contactId, updatedAt])
}

model Message {
  id             String       @id @default(cuid())
  conversationId String
  conversation   Conversation @relation(fields: [conversationId], references: [id])
  direction      Direction    // INBOUND | OUTBOUND
  body           String
  status         Status       @default(QUEUED)
  createdAt      DateTime     @default(now())

  @@index([conversationId, createdAt])
}

Accept the reply, deliver it later

The endpoint does two things and nothing more: write the outbound message, then hand delivery to a BullMQ queue. The provider call, retries and status updates live in a worker, so a slow WhatsApp API never blocks the request.

Guards and DTO validation sit in front. Redis backs the queue and the hot caches.

src/conversations/conversations.controller.tstypescript
@Post(':id/replies')
@UseGuards(JwtAuthGuard, WorkspaceGuard)
async reply(
  @Param('id') id: string,
  @Body() dto: ReplyDto,
  @CurrentUser() user: User,
) {
  const message = await this.messages.create({
    conversationId: id,
    direction: 'OUTBOUND',
    body: dto.body,
    authorId: user.id,
  });

  await this.outbound.add('send', { messageId: message.id }, {
    attempts: 3,
    backoff: { type: 'exponential', delay: 2000 },
    removeOnComplete: true,
  });

  return message; // status: QUEUED, the worker flips it to SENT
}

Show it sent before the server says so

The Next.js inbox renders the reply optimistically with a queued state, then reconciles with the server response. Agents see their message the instant they hit enter, which is what makes the inbox feel like a chat app and not a form.

Same API, in the agent's pocket

The Flutter app talks to the same endpoint through a Dio repository. A BLoC holds the conversation state, so the widget tree stays declarative and the network layer stays testable.

Clean architecture keeps the domain model shared across features, and the app ships in Arabic and English from day one.

lib/features/inbox/presentation/conversation_bloc.dartdart
class ConversationBloc extends Bloc<ConversationEvent, ConversationState> {
  ConversationBloc(this._repo) : super(const ConversationState.initial()) {
    on<ReplySent>(_onReplySent);
  }

  final ConversationRepository _repo;

  Future<void> _onReplySent(ReplySent e, Emitter<ConversationState> emit) async {
    final draft = Message.outbound(body: e.body, status: MessageStatus.queued);
    emit(state.copyWith(messages: [...state.messages, draft]));

    final result = await _repo.reply(conversationId: e.conversationId, body: e.body);

    result.fold(
      (failure) => emit(state.markFailed(draft.id, failure.message)),
      (sent)    => emit(state.replace(draft.id, sent)),
    );
  }
}
